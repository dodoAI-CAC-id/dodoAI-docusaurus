# ガイド: インフラストラクチャ開発入門（Terraform）

- このガイドを使用して、すべてのベースラインInfrastructure as Code（IaC）原則、必要なリポジトリ構造、Terraformベースの開発のベストプラクティスを定義してください。
- 一貫性があり、スケーラブルなインフラストラクチャ開発のために含めて維持すべき内容の文書化に焦点を当ててください。

---

## 定義すべき内容

### 1. IaC基礎

- Infrastructure as Code（IaC）は、すべてのインフラ/リソースプロビジョニングに必要です。
- コードは人間が読みやすく、機械実行可能で、バージョン管理されている必要があります。
- すべての設定は再現可能で監査可能なデプロイメントを可能にする必要があります。

### 2. 標準ツール: Terraform

- Terraformは、インフラストラクチャの記述、プロビジョニング、管理のための必須選択肢です。
    - 常に宣言的設定ファイル（`.tf`）を使用してください
    - バージョニング、plan/apply、ステート管理ワークフローを採用する必要があります

### 3. リポジトリ構造

- すべてのTerraformコードは、再利用と明確性のために環境、モジュール、リソースタイプごとに整理する必要があります。
    - ディレクトリレイアウトには以下を含める必要があります：
      ```
      environments/      # 環境固有の変数（dev、staging、prod）
      modules/           # 再利用可能なインフラストラクチャモジュール
      main.tf, variables.tf, outputs.tf, etc.  # ルート設定とエントリーポイント
      README.md          # すべてのプロジェクト設定とディレクトリ説明
      ```
- すべての環境固有設定（`*.tfvars`）とリモートステート設定が存在し、文書化されている必要があります。

### 4. 必要なTerraformコンセプト

- **プロバイダー:**  
  - すべてのクラウドと外部システムのプロバイダーは明示的に宣言される必要があります。
- **リソース:**  
  - すべてのインフラストラクチャオブジェクト（VPC、EC2、EKSなど）はリソースとして記述される必要があります。
- **変数/出力:**  
  - すべてのパラメータは検証付きで宣言され、モジュール間および外部消費のための出力が提供される必要があります。
- **モジュール:**  
  - 繰り返される構成要素にはモジュールを使用し、コードをDRY（Don't Repeat Yourself）に保ってください。
- **ステート管理:**  
  - リモートバックエンド（例：ロック用のS3 + DynamoDB）は必須です。
  - ステートは暗号化、バージョン管理され、認可されたユーザー/サービスのみがアクセス可能である必要があります。

### 5. ワークフロー要件

- **計画:**  
  - すべての変更は適用前に`terraform plan`でレビューが必要です。
- **開発:**  
  - すべての変更を最初に非本番環境で作成・テストしてください。
  - 各環境の適切な変数/設定セットアップに従ってください。
- **本番デプロイメント:**  
  - 手動レビュー/承認でのみ変更を適用してください。
- **テスト:**  
  - 適用前にvalidate、fmt、セキュリティ/ポリシーチェック（tfsec、conftest）、Terratestを使用してください。
- **コスト/タグ付け:**  
  - すべてのリソースはコスト追跡と所有者識別のためにタグ付けされる必要があります。

### 6. セキュリティベストプラクティス

- 機密データは安全なシークレット管理に保存してください（.tfファイルにハードコードしないでください）。
- デプロイメントに必要な最小権限にIAM権限を割り当ててください。
- インフラストラクチャ変更にチームコードレビューを強制してください。

---

**注意:**  
これらの定義と組織標準は、プロジェクトの主要READMEに含まれ、すべてのインフラストラクチャ開発とコードレビューで遵守される必要があります。
