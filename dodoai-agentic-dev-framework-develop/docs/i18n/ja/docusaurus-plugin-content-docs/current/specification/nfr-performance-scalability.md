# 定義ガイド – パフォーマンスとスケーラビリティ非機能要件

- このガイドを使用して、パフォーマンスとスケーラビリティの非機能要件を包括的に定義します。
- サンプル値をそのままコピーしないでください。ビジネスニーズ、システム特性、ライフサイクル、現実的な成長に基づいてカスタマイズしてください。
- どの要件が重要かを明確に示し、根拠、メトリクス、制約、将来性を考慮した検討事項を提供してください。

## 1. ビジネスワークロード

システムのパフォーマンスとスケーラビリティに影響するビジネス量に関する特性と前提を定義します。

### 1.1 定常状態でのワークロード
- **ユーザー数:** ユーザープロファイルを定義（特定ユーザー、固定上限、大規模/不特定の公開アクセス）
- **同時アクセス:** 同時セッションまたはリクエストを指定（単一、固定最大、多数/不特定）
- **データ量:** どのデータがどの程度含まれるかを特定（全データまたは主要データセットのみ）
- **オンラインリクエスト量:** プロセスごとのオンライントランザクション数を明確化（操作ごと、または主要操作のみ）
- **バッチ量:** バッチジョブの量を定義（各ジョブごと、または主要ジョブのみ）
- **ビジネス機能数:** ビジネス機能をリストアップして確認（固定、確定済み、未確定）
- **特別な考慮事項:** ワークロード要件は関連する場合、ピーク期間と季節性を考慮する必要があります

### 1.2 ワークロード成長率
システム開始からライフサイクル終了までのビジネスワークロードの予想成長を定義します。
- **ユーザー成長率:** 予想される倍率増加（例：1.2倍、2倍、3倍、10倍以上）
- **同時アクセス成長率:** 上記と同様、ただし同時負荷について
- **データ量成長率:** 将来のデータサイズ増加を予測
- **オンライン/バッチリクエスト成長:** 時間の経過とともに負荷がどのように上昇するかの期待値を設定
- **ビジネス機能成長:** より多くの機能が追加されるか？倍率を記載

### 1.3 データ保持期間
- **保持期間:** 異なるデータタイプ（ビジネス、ログ、システム）をどの程度保持する必要があるかを定義（例：1年、5年、10年以上、永続）
- **範囲:** オンラインデータのみが対象か、アーカイブ/オフラインストレージも必要かを明確に指定

## 2. パフォーマンス目標

### 2.1 オンライン応答時間
各シナリオで必要なシステム応答時間とコンプライアンス率を明確に指定します。
- **通常応答コンプライアンス:** 標準条件下で目標を満たすリクエストの割合（例：90%、95%、99%以上）
- **ピーク期間コンプライアンス:** ピーク負荷下でのコンプライアンス割合
- **劣化モードコンプライアンス:** フェイルオーバー、クラスター削減、または部分的なシステム停止の場合のコンプライアンス割合

### 2.2 バッチ処理ターンアラウンド時間
- **通常期間:** 設定時間内にジョブを完了する能力、または失敗時の再試行を許可
- **ピーク/劣化期間:** 同様、ただしより重い条件または不安定な条件下

### 2.3 オンラインスループット
- **通常スループット効率:** 実際対必要処理の比率（例：必要レートの2倍、3倍などをサポート）
- **ピーク/劣化スループット:** ストレス下での許容度と維持可能な最小レベルを定義

### 2.4 バッチスループット
- **通常/ピーク/劣化:** 上記と同様、定期的、大規模、または一回限りのバッチジョブについて
- **例:** 月次給与計算、年次移行、日次サマリージョブ

### 2.5 印刷（レポート）スループット
- **通常/ピーク/劣化:** 時間単位あたりのページまたはレポート、ピークとフォールバック計画を考慮

## 3. リソーススケーラビリティ

### 3.1 CPUスケーラビリティ
- **CPU使用率:** 望ましい使用目標と拡張のしきい値を定義（例：50%未満、80%未満）
- **CPU拡張:** CPUをどの程度拡張できるかを記載（例：2倍、8倍、拡張なし）

### 3.2 メモリスケーラビリティ
- **メモリ使用率:** 上記と同様、メモリについて（例：50%未満、80%未満）
- **拡張能力:** 許可または必要な倍率（例：2倍、4倍）

### 3.3 ディスクスケーラビリティ
- **ディスク使用率:** 使用目標と最大しきい値（例：70%未満）
- **拡張オプション:** 拡張の倍率（2倍、4倍など）、物理または仮想オプションを含む

### 3.4 ネットワークスケーラビリティ
- **ネットワーク範囲/スコープ:** 展開時にカバーされるネットワーク領域を定義（なし、単一LAN、オフィス間WAN/VPN、外部/パートナーサイトへの接続）
- **帯域幅保証:** ネットワーク帯域幅が保証されるかどうかとその方法を記載（例：なし、プロトコルごと、サーバーごと、アプリエンドツーエンド）

## 4. サーバーアップグレードと拡張

- **スケールアップ:** より高性能なサーバーへの置き換え—どの要素についてどの範囲で定義
- **スケールアウト:** 水平サーバーの追加—どの層、どのように分散、どのワークロードについて定義

## 5. パフォーマンス品質保証

### 5.1 リソース専有性
- **HWリソース専有性:** 重要なハードウェア（CPU、メモリ）が専用か共有かを定義。共有は他のテナント/ワークロードからのパフォーマンスリスクにつながります

### 5.2 パフォーマンステスト
- **測定頻度:** パフォーマンステストをどの程度の頻度でいつ実施するか？（なし、展開時、運用中のアドホック、継続的）
- **カバレッジ:** テストの範囲（全機能、主要機能、なし）
- **負荷スパイク処理:** 大規模で短期間のスパイクに対する前提と保護を記載（B2Cトラフィック急増、プロモーションイベントなど）

### 5.3 スパイク保護とトランザクション制限
- **トランザクション保護:** 同時トランザクションに上限はあるか？「申し訳ございません」ページ（優雅な拒否）や過負荷フォールバック用の専用サーバーはあるか？

---

**目的**

パフォーマンスとスケーラビリティ要件を明確に定義することで、システムが期待される性能レベルを維持し、ビジネス成長に対応できることを確保します。これらの要件は、アーキテクチャ設計、インフラ計画、運用戦略の基盤となります。
