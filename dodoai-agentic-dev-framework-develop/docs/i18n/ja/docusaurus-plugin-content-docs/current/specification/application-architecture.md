# マイクロサービスベースシステムにおけるアプリケーションアーキテクチャ定義ガイド

- このガイドを使用して、ビジネスプロセスの観点からマイクロサービスベースシステムのアプリケーションアーキテクチャを包括的かつ構造的に定義してください。
- サンプル図や文言を直接コピーしないでください。常に実際のシステム、ビジネス、コンテキストに合わせて構造と内容を適応させてください。
- 目的は、ビジネス、開発、運用全体で共通理解を可能にするドキュメント標準を作成することです。

---

## アプリケーションアーキテクチャで定義すべき内容

以下の側面を慎重に指定し、視覚化する必要があります：

### 1. アーキテクチャ概要と意図

- システムが実現する主要なビジネスフローやユーザージャーニーを明確に述べ、主要なアクター（ユーザー、システム、インターフェース）に焦点を当ててください。
- 核となるアーキテクチャ原則を説明してください：「サービス間の責任の構造と分離」であり、単なる技術コンポーネントやプロトコルではありません。
- 平易な言葉で「どのサービスがどのビジネスプロセスに責任を持ち、全体的なフローを達成するためにどのように相互作用するか」を説明してください。

### 2. 論理コンポーネント単位

明確性のために、各アーキテクチャ単位（マイクロサービスまたは機能単位）を定義し、説明してください：

- **ユーザー/エントリーポイント**: ユーザーや外部システムが操作をトリガーしたり、データを入力したりする方法と場所。
- **プレゼンテーション層**: サービスを公開するインターフェースコンポーネント（フロントエンド、モバイル、APIゲートウェイ/BFF）。
- **入力サービス**: 受信データやリクエストの処理に責任を持つサービス。
- **統合サービス**: オーケストレーション、検証、変換、またはサービス間ビジネスロジックに責任を持つサービス。
- **ストレージサービス**: データストア（トランザクション、参照、分析、不変など）の役割とその分離を定義。
- **バッチ/分析層**: リアルタイムマイクロサービスから定期的プロセス、レポート、集約ロジックを分離。
- **認証/認可サービス**: アクセス制御とアイデンティティ（ユーザーとサービス）の管理方法を概説。

### 3. 責任マッピングとフロー視覚化

- 各ビジネスプロセスまたはドメインコンテキストについて、どのマイクロサービスが各主要責任を所有するかをマッピングしてください。
- ワークフローの一部として、単位間の引き継ぎ/通信を明示的にしてください（図の矢印や順次コールアウトを使用）。
- 該当する場合、データ系統を説明してください：データがエリア間でどのように流れ、どのサービスが記録のソースかを示してください。

### 4. 拡張とスケーラビリティのサポート

- アーキテクチャが将来の成長をどのようにサポートするかを明確にしてください：新しいビジネスプロセス、マルチテナンシー、サービスやストレージの水平スケーリング。
- システムがSaaSを対象とする場合、新しいテナントやドメインをどのように追加、分離、管理できるかを記載してください。

### 5. 技術に依存しないパターンと再利用性

- ベンダー固有のツールやプログラミング言語ではなく、抽象的なアーキテクチャパターンに焦点を当ててください。
- 可能な限り、業界の垂直分野や技術スタックに依存しないサービス境界と相互作用を定義してください。
- これにより、将来のリファクタリングが導かれ、プロジェクト間でアーキテクチャドキュメントを共有することができます。

### 6. 視覚的表現（推奨：Mermaidまたは類似）

- 一貫した記法（Mermaidなど）を使用してアーキテクチャを視覚化してください。
- 各ブロック/ノードは、個々のサーバーや技術プロセスではなく、論理的責任/ビジネスサービスを表します。
- メインワークフローと高度/オプション要素（例：テナントサポート、ハイブリッドバッチ/リアルタイムフロー、非同期通信）の両方を描画し、説明してください。
- アーキテクチャが進化したり、新しいプロセスエリアが追加されたりした際の更新を促進してください。

### 7. 高度な設計考慮事項

該当する場合、以下を明示的に説明してください：
- サービスまたはデータ層でのマルチテナンシーとテナント分離アプローチ
- イベント駆動（Pub/Sub、Kafka、非同期メッセージング）アーキテクチャの使用
- リアルタイムとバッチデータフローまたは計算の統合

### 8. ドキュメントとコミュニケーション

- すべてのアーキテクチャドキュメントが開発者、アーキテクト、ビジネス関係者にアクセス可能であることを確認してください。
- アーキテクチャ図をビジネスプロセスモデリングとシステム/ソフトウェア設計の「橋渡し」として使用してください。
- アーキテクチャドキュメントを生きた成果物として維持し、重要なプロセスやインフラストラクチャの変更ごとに見直し、更新してください。

---

**このガイドの使用方法:**
マイクロサービスベースアプリケーションをアーキテクチャ設計または見直しする際は、上記の観点を定義チェックリストおよびドキュメント標準として使用してください。すべてのビジネスプロセスと技術機能について、責任所有権、制御とデータのフロー、スケーラビリティと拡張アプローチ、境界定義、システム全体の統合方法を明確にしてください。
