## プロジェクト管理

## プロジェクトルール

### 前提条件

現在のメンバーおよびアクセス権の制限を考慮した上で、効率的な方法を採用する。

### プロジェクト管理

GitHubをプロジェクト管理ツールとして使用する。

#### Issue管理

作業を行う際は、必ずIssueを作成し、タスクをIssue単位で管理する。  
Pull Request（PR）を作成する際は、必ずIssueにリンクさせる。  
Issueには以下の情報を含める。

"開始日" と "期限日" を定期的に確認し、"ラベル" カラムで設定された優先度と組み合わせて、作業の優先順位と実行スケジュールを調整する。

- **Issueのクローズ**
  - Pull Requestがある場合は、PRがマージされると自動的にクローズされる。
  - Pull Requestがない場合：割り当てられたタスクを完了後、ステータスを"DONE"に更新し、IssueのコメントまたはSlackで担当者に報告する。その後、担当者がCLOSEする。

- **プロジェクト**
  - GitHubの仕様上、どのプロジェクトに属するかを選択する必要がある。
- **目的**
  - Issueの目的を記載する。
- **Key Result（KR）**
  - Issueをクローズするために達成すべき内容を定義する。開発の場合：開発のゴールを記述。問い合わせの場合：クローズするために明確にすべき点を記述。
- **担当者**
  
  - Issueの解決を担当する人物を1人割り当てる（基本的に1人）。
  - 
- **提案**
  - 解決方法を記載する。
- **期限日**
  - 作成時に未確定の場合は、作業開始前に記載する。
- **マイルストーン**
  - マイルストーンを選択する。マイルストーンは機能単位と一致させる。
- **テスト証跡**
  - 開発作業の場合はスクリーンショットを添付する
  - （例：画像、スプレッドシート）。

#### Pull Request（PR）

リソースに変更がある場合は、必ずPRを作成する。  
PRはIssueに関連付けること。Issueと紐づいていないPRは、レビュアーがマージしないようにする。

PRを作成する際は、以下を含める：

- PRの説明を記載
- 証跡（動画・画像）を追加
- レビュアーを設定
- 自分を担当者として設定
- Issueにリンク（1 PR : 1 Issue）
- SSツール実行ログURLを添付（例：https://58llm.link/main/restore/5bd67ea1-ffe3-4e17-b6ba-d2366abee334）

#### マージ基準

以下の条件を満たしてからマージする：

- レビュアーの承認が必要
  - メインブランチ：2人の承認,開発/機能ブランチ：1人の承認
- レビュー時の全フィードバックが "Resolve Conversation" になっている
- CIが正常に通過している
- SSツールでAIエージェントによるテスト完了・コードレビュー済み

#### ステータス

GitHubには以下のステータスがある。各Issueにステータスを設定し、進捗を把握できるようにする。

- New, Backlog, Todo, In Progress, In Review, Done

### ソースコード管理

GitHubを使用してソースコードを管理する。  
"main" と "develop" を主要ブランチ
"feature"、"release"、"hotfix"、"prototype" を補助ブランチとして使用する。

#### メインブランチ

- **main**
  - 常にリリース可能な状態を反映するメインブランチ。リリースブランチからのみマージする。
- **develop**
  - 次回リリースに向けた最新の開発作業が反映されるブランチ。通常のPRのマージ先。

#### サポートブランチ

- **feature**
  - 新機能開発に使用。
  - リリーススケジュールの変更に柔軟に対応するため、機能ブランチを2種類に分ける。
    - `feature/feature_name`
      - API: `feature/api_{機能名}_#{Issue番号}`
      - フロントエンド: `feature/frontend_{機能名}_#{Issue番号}`
      - スマートコントラクト: `feature/smartcontract_{機能名}_#{Issue番号}`
      - インフラ: `feature/infra_{機能名}_#{Issue番号}`
      - ドキュメント: `feature/doc_{機能名}_#{Issue番号}`
    - 機能開発の場合、Epic名と一致させる。
    - 開発者のローカルリポジトリにのみ存在し、originにはプッシュしない。
- **release** *このプロジェクトでは使用しません*
  - リリース準備用のブランチ。リリースメタデータ（バージョン番号、ビルド日など）を準備する。
- **hotfix**
  - 重大なバグを緊急修正する際に使用。masterブランチから作成。
- **prototype**
  - 研究用のサンプルコードをコミットする際に使用。

### 進捗管理

GitHubのプロジェクトボードとNotionを活用して進捗を管理する。

### タスク管理


開発タスクのレビュー中。PR作成時には以下を実施：

- PRの説明を記載
- 証跡（動画・画像）を追加
- レビュアーを設定
- 自分を担当者として設定
- Issueにリンク（1 PR : 1 Issue）
- SSツール実行ログURLを添付（例：https://58llm.link/main/restore/5bd67ea1-ffe3-4e17-b6ba-d2366abee334）

- **Waiting for Deployment**: 本番環境への反映待ち
- **Done**:
 完了したIssueを配置

## バージョン管理

### 記法

以下の記法を使用  
`vX.Y.Z`（例：v1.2.3）

### バージョン付け

ドキュメント・プログラムのバージョン管理は以下の通り。

- **X（メジャーバージョン）**
  - 画面や操作性に影響を与える大規模変更やページ追加
- **Y（マイナーバージョン）**
  - 機能改善、小規模な情報追加、ページ修正など
- **Z（パッチバージョン）**
  - バグ修正、誤字修正など

### リリースノート

リリースノートは以下で管理されます。

リリースノートには以下の内容を含めてください。

- 機能追加
- 改善点
- ドキュメント更新

## 振り返り（Lessons Learned）

- **認識の統一**: タスクを依頼された際は、完全に理解するまで確認する。
  （例：課題点 / 何を / なぜ / どのようにするかを質問し、背景を把握する）
