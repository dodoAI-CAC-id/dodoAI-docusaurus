# ガイド: マイクロサービス API テストシナリオ

- このガイドは、マイクロサービスアーキテクチャのAPIテストシナリオを定義する方法を説明し、Cucumber（Gherkin）などのBDDスタイル形式を使用したインターフェース（コントラクト）テストに特化しています。
- 実装やテスト理論は追加せず、テストシナリオとして記述すべき内容とシナリオ定義の構造化方法のみを定義します。

---

## 定義すべき内容

### 1. APIエンドポイントまたはビジネスフローごとのテストシナリオ

- Gherkinまたはそれに相当するBDD構文を使用して各シナリオを記述します：
  - **Feature**/ScenarioヘッダーでAPIエンドポイントとフィーチャーを明確に記述します。
  - 以下のテストステップを定義します：
    - 正常フロー（「ハッピーパス」）
    - エッジ/エラーケース（無効なデータ、未認証、重複、レート制限など）
    - 統合フロー（サービス間/APIまたはイベントフロー）

### 2. シナリオコンポーネント

- **Feature:** 高レベルのビジネスプロセスまたはユーザーストーリーを簡潔に記述します。
- **Scenario:** 
  - 前提条件（**Given**）
  - アクション（**When**）
  - 期待結果（**Then**、およびオプションで**And**）

- 必要に応じて、Gherkinテーブルを使用して入力または期待レスポンスの複数のデータセットを指定します。

### 3. サービス間およびエッジケースのカバレッジ

- 成功と失敗/エラーユースケースの両方のシナリオを含めます。
- マイクロサービスについては、以下を含む統合シナリオを定義します：
  - 複数のサービス呼び出しまたはチェーン
  - イベントまたはメッセージフロー（イベント駆動システムなど）
  - 認証、認可、および分離ケース

### 4. データと環境

- 必要なテストデータ（ユーザー、製品、注文など）を事前に定義し、別のテストフィクスチャ/設定ファイルに文書化します。
- シナリオ実行に必要なテスト環境/設定を指定します：URL、トークン、モックなど。

### 5. 実行順序とメンテナンス

- 各シナリオは特定のビジネスまたはAPI要件にトレーサブルである必要があります。
- サービス、フィーチャー、またはエンドポイントごとにファイルを整理し、コントラクトまたはビジネスルールの変更に応じてシナリオを更新します。

---

## シナリオ例（Gherkin）

```gherkin
Feature: ユーザー登録
  新規ユーザーとして、
  アカウントを登録したい、
  ログインしてシステムを使用できるように

  Scenario: 登録成功
    Given 私は新規ユーザーでメールアドレスが "user@example.com"
    When パスワード "SecurePass123!" で登録する
    Then ステータス 201 Created を受信すべき
    And メール確認リンクを受信すべき
    And メール確認まではアカウントは未確認状態であるべき

  Scenario: 重複メールアドレス
    Given メールアドレス "user@example.com" のユーザーが存在する
    When 同じメールアドレスで再度登録を試行する
    Then ステータス 409 Conflict を受信すべき
    And エラーメッセージに "email already exists" が表示されるべき
```
