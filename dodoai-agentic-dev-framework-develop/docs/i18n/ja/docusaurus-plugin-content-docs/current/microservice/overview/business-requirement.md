# ガイド: マイクロサービス ビジネス要件の定義

- このガイドを使用して、マイクロサービスベースのアーキテクチャを推進する主要なビジネス目標、機能範囲、制約を定義します。
- サンプルセクションをそのままコピーしないでください。ビジネスコンテキスト、実際のステークホルダー、必要なメトリクスに適応させてください。
- ビジネス価値、サービス範囲、チームの責任、システムの非交渉事項の観点から定義すべき内容を明確にすることに焦点を当ててください。

---

## 定義すべき内容

### 1. ビジネスコンテキスト

- **ビジネス目標:**  
  - マイクロサービス採用の明確な根拠を定義（例：スケーラビリティ、回復力、チーム自律性、技術多様性）。
  - アーキテクチャがサポートするように設計された意図されたビジネス影響と成長または市場目標を述べる。

- **ステークホルダー要件:**  
  - 各主要ステークホルダーグループをリストアップ（例：プロダクトチーム、運用、ビジネスユーザー、開発者）。
  - ビジネスとシステムの両方からの具体的なニーズと期待を文書化（例：独立デプロイ、監視、高可用性、技術柔軟性）。

---

### 2. 機能要件

- **サービス境界:**  
  - コアドメインサービスを定義（例：ユーザー管理、注文処理、在庫、通知、分析）。
  - 各サービスが提供すべき主要なビジネス機能を明確に指定。
  - サービス責任の重複がないことを確保。

- **サービス間要件:**  
  - 以下の要件を指定:
    - サービス発見/セッション登録
    - サービス間通信プロトコル（REST、gRPC、イベント）
    - データ整合性と同期アプローチ（イベント駆動、結果整合性、APIベース）
    - システム全体のアーキテクチャ要求（イベント駆動設計、契約ベース統合）。

---

### 3. ビジネスルール

- **データ所有権:**  
  - 各サービスはそのデータストレージを排他的に所有する必要があります。サービス間の直接データアクセスは禁止。
  - データの共有方法を定義（APIのみ、イベントのみ、直接DB接続は禁止）。
  - 同期またはデータ更新ルールとポリシーを記述。

- **サービス独立性:**  
  - サービスは独立して開発、デプロイ、スケール、保守される。
  - チームは各サービスを所有し、すべてのライフサイクルイベント（開発、デプロイ、サポート）に責任を持つ。
  - 正当化される場合、サービスごとに技術スタックを選択可能（ポリグロットサポート）。

- **パフォーマンス要件:**  
  - ビジネスクリティカルフローのレイテンシ、応答時間、スループット、障害回復の最小基準を定義。
  - スケーリングと優雅な劣化（ストレス/負荷下でのフェイルオーバー、フォールバック動作）を指定。

---

### 4. ビジネス制約

- **コンプライアンス:**  
  - システムを制約するドメイン固有の規制（データプライバシー、会計/監査、取引セキュリティなど）をリストアップ。
  - 法的要求に従った監査可能性、ログ保持、プライバシー制限を指定。

- **統合:**  
  - レガシー（モノリス）システム、サードパーティAPI、バージョニング制約とのインターフェース要件を述べる。
  - 必要な移行とデータポータビリティ戦略を記述。

---

### 5. 成功メトリクス

- **ビジネスメトリクス:**  
  - システム価値の明確で測定可能な目標を特定:
    - 新機能の市場投入時間
    - システム可用性/稼働時間
    - 顧客満足度またはNPS
    - チーム生産性または速度

- **技術メトリクス:**  
  - ビジネス目標をサポートする技術成功メトリクスを定義:
    - デプロイ頻度とリードタイム
    - 平均復旧時間（MTTR）
    - トランザクション/サービス応答時間
    - エラー率、障害分離、障害回復

---

## ドキュメントガイドライン

- 各要件またはルールについて、以下を指定:
  - なぜ重要か（ビジネス根拠）
  - 誰が関心を持つ/所有するか（ステークホルダーまたはチーム）
  - どのように測定されるか（メトリック、閾値、またはポリシー）
- 市場、ステークホルダー、技術環境の進化に応じて、ビジネス要件を定期的にレビュー。
- 継続的な整合性を確保するため、ビジネス要件をアーキテクチャ、サービス契約、配信ロードマップに統合。

---

**目的**

この構造により、マイクロサービスシステムのビジネス推進要因と制約が明示的、測定可能、実行可能になり、アーキテクチャが継続的なビジネスニーズ、コンプライアンス、ステークホルダー価値を直接サポートできるようになります。
