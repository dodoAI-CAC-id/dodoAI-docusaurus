# 見守りシステム マイクロサービスAPI 実装計画

**作成日:** 2025年10月29日  
**プロジェクト:** 異常検知・通知・現場対応システム API

## 📊 概要

### 現状
- Gin Frameworkベースのシンプルなユーザー管理API
- PostgreSQL + Docker環境
- 基本的なCRUD操作のみ

### 目標
- 介護施設向け異常検知・通知・現場対応システムの包括的なマイクロサービスAPI
- 11のエンティティ（Incident, Notification, Action, Person, Staff, Department, Room, CameraDevice, DetectionArea, IncidentVideo, AuditLog, Configuration）
- 40以上のエンドポイント
- 複雑なリレーション管理（ER図参照）

#### 2.2 リレーション管理

**重要なリレーション:**
```
Incident (1) --> (N) Notification
Incident (1) --> (N) Action
Incident (1) --> (N) IncidentVideo
Person (1) --> (N) Incident
CameraDevice (1) --> (N) Incident
Room (1) --> (N) Person
Room (1) --> (N) CameraDevice
```

**実装方針:**
- 外部キー制約を活用
- JOINクエリで関連データを効率的に取得
- N+1問題を回避するため、必要に応じてプリロード

### Phase 3: ハンドラー実装

#### 3.1 Incidentハンドラー（最重要）
**ファイル:** `internal/handlers/incident_handler.go`

**エンドポイント:**
1. `GET /api/v2/incidents`
   - 異常イベント一覧取得
   - クエリパラメータ: personId, from, to, status
   - フィルタリング・ソート機能

2. `POST /api/v2/incidents`
   - AI検知による異常イベント登録
   - 必須: detectedAt, type, personId, cameraId
   - 自動通知トリガー

3. `GET /api/v2/incidents/{incidentId}`
   - 異常イベント詳細取得
   - 関連データ（notifications, actions, videos）を含む
   - 検知画像（base64）を含む

4. `PATCH /api/v2/incidents/{incidentId}`
   - イベント情報更新
   - status, description, detectionAreaId

#### 3.2 Notificationハンドラー
**ファイル:** `internal/handlers/notification_handler.go`

**エンドポイント:**
1. `GET /api/v2/notifications`
   - 通知履歴検索
   - クエリパラメータ: staffId, incidentId, unreadOnly

2. `POST /api/v2/notifications`
   - 手動通知作成・再送
   - 通知対象スタッフID配列

3. `POST /api/v2/notifications/{notificationId}/mark-read`
   - 既読フラグ登録
   - リクエストボディ: staffId

4. `POST /api/v2/notifications/{notificationId}/escalate`
   - エスカレーション発動
   - 上位者への通知

#### 3.3 Actionハンドラー
**ファイル:** `internal/handlers/action_handler.go`

**エンドポイント:**
1. `GET /api/v2/incidents/{incidentId}/actions`
   - 異常ごとの対応履歴取得
   - 部屋/ベッド名称、対象者名、異常検出動作を含む

2. `POST /api/v2/incidents/{incidentId}/actions`
   - 対応登録/進捗切替
   - actionType: start/complete/escalate
   - progress: in_progress/completed/monitoring

#### 3.4 Person/Staff/Room/Cameraハンドラー
**ファイル:** `internal/handlers/person_handler.go` 他

**共通パターン:**
- `GET /api/v2/{resource}` - リスト取得

- `POST /api/v2/{resource}` - 新規作成
- `PATCH /api/v2/{resource}/{id}` - 更新
- `DELETE /api/v2/{resource}/{id}` - 削除（必要に応じて）

#### 3.5 IncidentVideoハンドラー
**ファイル:** `internal/handlers/incident_video_handler.go`

**エンドポイント:**

2. `GET /api/v2/videos/{videoId}/file`
   - 動画ファイル実体取得

#### 3.6 AuditLogハンドラー

**実装:**

func AuditLogMiddleware(db *sql.DB) gin.HandlerFunc {
    return func(c *gin.Context) {
        // リクエスト前処理
        startTime := time.Now()
        
        // リクエスト処理
        c.Next()
        
        // リクエスト後処理（ログ記録）
        duration := time.Since(startTime)
        // audit_logsテーブルに記録
    }
}

## 🔑 重要な技術的考慮事項

### 1. リレーション管理
- **課題:** `Incident`を中心とした複雑なリレーション
- **対策:**
  - 適切なJOINクエリの使用
  - N+1問題の回避（必要に応じてプリロード）
  - インデックスの最適化

### 2. 画像・動画処理
- **課題:** 大容量ファイルの扱い
- **対策:**
  - 検知画像: Base64エンコーディング
  - 動画ファイル: ストリーミング対応
  - ファイルストレージ管理（将来的にS3等を検討）

### 3. 通知システム
- **課題:** リアルタイム性、未読管理
- **対策:**
  - 未読管理: `unreadByStaffIds`配列で管理
  - エスカレーション: タイムアウト設定
  - 通知履歴: `notification_histories`テーブルで追跡

### 4. 監査ログ
- **課題:** 全操作の記録による性能影響
- **対策:**
  - 非同期処理（Goroutine）
  - バッチインサート
  - 適切なインデックス

### 5. データ整合性
- **課題:** 複雑なトランザクション
- **対策:**
  - トランザクション管理の徹底
  - 外部キー制約
  - バリデーションの強化
